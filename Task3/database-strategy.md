# Выбор баз данных и обеспечение RPO/RTO

## 1. Выбор баз данных

| Сервис | Тип базы данных | Обоснование | RPO | RTO |
|---|---|---|---|---|
| **Сервис ставок** | PostgreSQL (реляционная) | Структурированные данные о ставках, необходимость ACID-транзакций, обеспечения целостности и быстрого поиска ставок по рекламным позициям. | ≤ 1 мин | ≤ 15 мин |
| **Сервис кампаний** | PostgreSQL (реляционная) | Хранение взаимосвязанных сущностей кампаний, рекламных объявлений и настроек таргетинга. Поддержка транзакций и ссылочной целостности. | ≤ 5 мин | ≤ 30 мин |
| **Сервис статистики** | ClickHouse (колоночная OLAP СУБД) | Хранение большого объёма структурированных событий показов и кликов. Колоночная организация данных обеспечивает эффективные агрегации по кампаниям, рекламным позициям и временным интервалам. | ≤ 15 мин | ≤ 1 ч |
| **Сервис аналитики** | ClickHouse (колоночная OLAP СУБД) | Построение аналитических отчётов, выполнение сложных агрегирующих запросов по большим объёмам исторических данных. Возможность использовать материализованные представления. | ≤ 24 ч | ≤ 8 ч |
| **Сервис финансов** | PostgreSQL (реляционная) | ACID-транзакции, атомарное резервирование бюджета, контроль остатков, идемпотентность финансовых операций и ведение журнала транзакций. | **0 мин** | ≤ 15 мин |

Указанные RPO/RTO являются целевыми требованиями для отказа одного узла или одной зоны доступности. Выполнение требований должно быть подтверждено регулярным тестированием восстановления. Полная потеря региона и логическое повреждение данных рассматриваются как отдельные аварийные сценарии.

## 2. Механизмы обеспечения RPO/RTO

### Сервис ставок — RPO ≤ 1 мин, RTO ≤ 15 мин

**Обеспечение RPO:**
- Основная PostgreSQL и асинхронная standby-реплика размещаются в разных зонах доступности.
- Используется потоковая репликация WAL.
- Контролируется отставание реплики по времени и LSN. При превышении допустимого порога система прекращает подтверждать новые изменения ставок до восстановления требуемого уровня защиты.
- Настраиваются регулярные резервные копии и архивирование WAL для восстановления на определённый момент времени (PITR).

**Обеспечение RTO:**
- Patroni контролирует состояние PostgreSQL и обеспечивает переключение на пригодную реплику.
- После переключения обновляется маршрутизация подключений.
- Выполняются проверки доступности API ставок и корректности данных.

### Сервис кампаний — RPO ≤ 5 мин, RTO ≤ 30 мин

**Обеспечение RPO:**
- PostgreSQL с асинхронной репликацией между зонами доступности.
- Мониторинг задержки репликации с целевым пределом 5 минут и ограничением записи при нарушении допустимого отставания.
- Периодические полные резервные копии и непрерывное архивирование WAL.

**Обеспечение RTO:**
- Переключение на актуальную standby-реплику через Patroni.
- Переподключение CampaignService к новому primary.
- Восстановление и актуализация кэша кампаний.
- Проверка доступности кампаний, их статусов и параметров таргетинга.

### Сервис статистики — RPO ≤ 15 мин, RTO ≤ 1 ч

**Обеспечение RPO:**
- Используется ClickHouse с таблицами семейства ReplicatedMergeTree и репликами в разных зонах доступности.
- События показов и кликов сначала записываются в Kafka с репликацией, после чего асинхронно загружаются в ClickHouse.
- Kafka настроена с `replication.factor=3`, `min.insync.replicas=2`, `acks=all`.
- Исходные события сохраняются в Kafka минимум 7 дней, что позволяет повторно обработать их при потере данных ClickHouse.
- Для восстановления данных применяются контроль смещений Kafka и повторная обработка событий с дедупликацией по `eventId`.

**Обеспечение RTO:**
- При отказе узла запросы переключаются на доступную реплику ClickHouse.
- Если данные повреждены, таблицы восстанавливаются из резервных копий и событий Kafka.
- После восстановления выполняется проверка количества событий и корректности агрегатов.

### Сервис аналитики — RPO ≤ 24 ч, RTO ≤ 8 ч

**Обеспечение RPO:**
- ClickHouse используется для хранения аналитических витрин и исторических агрегатов.
- Настраиваются ежедневные резервные копии с хранением в независимом объектном хранилище.
- Исходные данные сохраняются в статистическом хранилище и долговременном архиве событий.
- При потере аналитических данных отчёты могут быть восстановлены повторным выполнением ETL-процессов.

**Обеспечение RTO:**
- Восстановление аналитического кластера из резервной копии.
- Перезапуск ETL-процессов и восстановление материализованных представлений.
- Проверка корректности агрегатов и доступности отчётов.

Статистика и аналитика используют одну технологию хранения, но обслуживают разные нагрузки. Для предотвращения взаимного влияния могут применяться отдельные кластеры ClickHouse.

### Сервис финансов — RPO = 0 мин, RTO ≤ 15 мин

Финансовые операции являются критичными, поэтому потеря подтверждённых операций резервирования, пополнения и списания бюджета недопустима.

**Обеспечение RPO = 0:**

1. PostgreSQL развёрнута в трёх зонах доступности: один primary и две standby-реплики.
2. Используется синхронная потоковая репликация WAL как минимум на одну standby в другой зоне доступности.
3. Для финансовых транзакций устанавливается `synchronous_commit=on` и настраивается `synchronous_standby_names`, чтобы подтверждение `COMMIT` ожидало сохранения WAL на primary и синхронной standby.
4. Успешный ответ клиенту возвращается только после подтверждения транзакции PostgreSQL. До этого финансовая операция не считается подтверждённой.
5. Если синхронная реплика недоступна и нет другой пригодной синхронной реплики, новые финансовые операции не подтверждаются. Автоматический переход на асинхронную запись запрещён.
6. В случае отказа primary новый primary выбирается только из реплик, содержащих все подтверждённые транзакции.
7. Перед переключением прежний primary изолируется (fencing): прекращаются его записи и клиентские подключения. Для защиты от split-brain используются кворумный механизм Patroni и watchdog.
8. Для операций применяются уникальные идентификаторы и ограничения уникальности, исключающие повторное резервирование или списание при повторном запросе.

Таким образом, RPO = 0 обеспечивается для подтверждённых финансовых транзакций в пределах модели отказа одной зоны доступности, при сохранности синхронной копии данных.

**Роль Hibernate и Kafka:**

Hibernate используется для работы приложения с PostgreSQL, но сам по себе не обеспечивает репликацию и сохранность транзакций.

Kafka применяется для асинхронного распространения финансовых событий. Для этого используется Transactional Outbox: изменение финансовых данных и создание записи исходящего события выполняются в одной транзакции PostgreSQL. После фиксации транзакции событие публикуется в Kafka.

**Источником истины остаётся PostgreSQL, а не Kafka.**

**Обеспечение RTO ≤ 15 мин:**

- Patroni обнаруживает недоступность primary.
- Кворумный механизм подтверждает право на переключение.
- Прежний primary изолируется от приёма новых записей.
- Синхронная реплика с подтверждёнными транзакциями становится новым primary.
- Приложение переключает подключения на новый primary.
- Выполняются проверки целостности финансовых данных, после чего возобновляются операции.

Целевое время восстановления при отказе primary или одной зоны доступности — не более 15 минут.

## 3. Резервное копирование и PITR финансовой базы данных

Для защиты от логических ошибок, удаления данных и повреждения БД дополнительно используется резервное копирование.

**Стратегия резервирования:**

- Ежедневное создание базовых физических резервных копий PostgreSQL.
- Непрерывное архивирование WAL.
- Хранение резервных копий и WAL в отдельном объектном хранилище, изолированном от основного кластера.
- Шифрование резервных копий и защита от удаления.
- Регулярная проверка успешности резервирования и тестовое восстановление.

**Восстановление с помощью PITR:**

1. Определяется момент возникновения ошибки или повреждения данных.
2. Создаётся новый экземпляр PostgreSQL в изолированной среде.
3. Восстанавливается последняя подходящая базовая резервная копия.
4. Воспроизводятся архивные WAL до выбранной точки восстановления.
5. Проверяется целостность базы данных.
6. Выполняется сверка балансов и финансовых операций.
7. После подтверждения корректности восстановленная база вводится в эксплуатацию.

PITR позволяет восстановить состояние на определённый момент, но сам по себе не гарантирует RPO = 0. Для восстановления самых последних подтверждённых транзакций необходима сохранная синхронная реплика либо другой долговечный источник их полного журнала.

## 4. Проверка финансовых данных после восстановления

Перед возобновлением финансовых операций выполняются следующие проверки:

- Все подтверждённые транзакции присутствуют в журнале операций.
- Для каждой кампании выполняется инвариант: `доступный бюджет = общий лимит − списанная сумма − зарезервированная сумма`.
- Финансовые балансы соответствуют операциям в журнале транзакций.
- Отсутствуют повторные списания с одинаковым идентификатором операции.
- Резервы находятся в допустимых состояниях: `RESERVED`, `CAPTURED` или `RELEASED`.
- Проверяется отсутствие отрицательного доступного бюджета.
- Незавершённые и неоднозначные операции сверяются по идентификаторам и при необходимости обрабатываются повторно идемпотентным способом.

При обнаружении расхождений финансовые операции не возобновляются до восстановления корректного состояния.

## 5. Проверка выполнения RPO/RTO

Для подтверждения заявленных показателей проводятся регулярные учения:

- Отключение primary PostgreSQL и проверка автоматического переключения.
- Проверка отсутствия потери подтверждённых финансовых операций.
- Проверка блокирования записи при недоступности синхронных реплик.
- Восстановление PostgreSQL из backup и WAL.
- Восстановление ClickHouse из реплик, резервных копий и событий Kafka.
- Фиксация фактического времени восстановления и величины потери данных.

Показатели RPO/RTO считаются подтверждёнными только после успешного прохождения испытаний на данных и нагрузке, сопоставимых с продуктивной средой.
